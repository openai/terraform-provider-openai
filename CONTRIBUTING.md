# Contributing to the OpenAI Terraform Provider

Thank you for helping improve the OpenAI Terraform provider and its release
artifacts. Read [README.md](README.md) for provider setup,
[RELEASING.md](RELEASING.md) for release and signing requirements, and
[SECURITY.md](SECURITY.md) for private vulnerability reporting.

## Development workflow

Use the Go version declared in `go.mod` and a supported Terraform CLI. For
ordinary changes, run the focused checks relevant to your change:

```sh
make build
make test
terraform fmt -check -recursive examples
```

Run `make lint` when `golangci-lint` is available. Do not set `TF_ACC=1` or
run `make testacc` and related acceptance targets without explicit maintainer
authorization, disposable resources, and appropriately scoped credentials:
acceptance tests can call live Administration APIs and mutate organization
resources.

## Generated code and documentation

Files listed in `.terraform-generator-manifest.json` and files marked
`Code generated by generate-terraform-provider. DO NOT EDIT.` are
generator-owned. Much of `internal/provider/`, `docs/`, `examples/`,
`templates/`, the Go module files, and CI configuration falls into this
category. Coordinate changes to generated files with the upstream generator
owners instead of hand-editing generated output.

`make generate` invokes `tfplugindocs` through `tools/` and regenerates
Terraform Registry documentation; it does not regenerate the provider
implementation. Regenerate documentation only when necessary, and review all
resulting changes.

## Security requirements

- **Secrets and fixtures:** Never commit live API keys, access tokens, signing
  keys, private certificates, credentials, or customer data. Load the provider's
  Admin API key from `OPENAI_ADMIN_KEY`, use clearly fake values in examples
  and fixtures, and keep Terraform state, plans, outputs, and `.tfvars` files
  free of real secrets. Preserve sensitive provider schema attributes such as
  `admin_api_key`.
- **Logs and diagnostics:** Redact authorization headers, cookies, tokens,
  signed URLs, credential-bearing query parameters, organization/project
  identifiers, customer data, and sensitive request/response bodies from
  Terraform diagnostics, crash reports, `TF_LOG` output, fixtures, and CI
  artifacts.
- **Dependencies:** Review direct and transitive dependency changes in
  `go.mod`, `go.sum`, `tools/go.mod`, and `tools/go.sum`, including module
  sources, `replace` directives, checksums, generators, and install/build
  scripts. Review provider sources and checksums in `.terraform.lock.hcl` when
  applicable, and do not accept unexplained dependency or lockfile changes.
- **CI and publishing:** Pin third-party GitHub Actions to full commit SHAs,
  grant minimum workflow/job permissions, and isolate untrusted pull-request
  code from credentials. Preserve the protected `release` and `publish`
  environments; protect `OPENAI_SDKS_APP_PRIVATE_KEY`, `GPG_PRIVATE_KEY`, and
  `PASSPHRASE`; and maintain provider release archives, GPG-signed checksums,
  per-archive SPDX SBOMs, the Terraform Registry manifest, and release SBOM
  verification.
- **Sensitive changes:** Request maintainer or `@openai/sdks-team` review for
  authentication, `base_url`, redirects, TLS, organization/project isolation,
  Terraform schema/state, resource import, path/query serialization, logging,
  generated code, dependencies, and CI/release changes. Add focused regression
  or security tests for affected credential, network, state, serialization, or
  publishing boundaries.
- **Vulnerability reports:** Report vulnerabilities in the provider or its
  release artifacts privately through [SECURITY.md](SECURITY.md) and
  `disclosure@openai.com`. Never report a suspected vulnerability in a public
  GitHub issue, pull request, or discussion.
